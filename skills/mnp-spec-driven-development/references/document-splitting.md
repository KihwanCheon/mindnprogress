# 문서 분할과 통합 관리

## 분할 목표

각 문서는 독립적으로 범위와 완료를 판정할 수 있어야 하고, 여러 AI가 동시에 작업해도 공유 코드·Prefab 충돌이 최소화되어야 한다. 슬라이드 수는 규모 신호일 뿐 분할 기준이 아니다.

## 분할 판단 기준

다음 질문에 대한 답이 달라지는 경계에서 문서를 나눈다.

- 어떤 사용자 흐름을 독립적으로 Play할 수 있는가?
- 어떤 상태와 데이터의 소유자가 같은가?
- 어떤 화면·씬·Prefab을 수정하는가?
- 어떤 서버 API와 외부 전달물에 의존하는가?
- 어떤 이벤트를 생산하고 어떤 기능이 소비하는가?
- 다른 문서와 독립적으로 구현·검수·완료할 수 있는가?
- 별도 작업공간에서 병렬로 수정해도 통합 충돌이 적은가?

한 문서가 여러 독립 기능을 대표 체크리스트 몇 개로 묶게 되면 더 분할한다. 반대로 같은 상태와 Prefab을 여러 문서가 함께 수정해야 한다면 소유 문서를 하나로 합치거나 공통 계약과 통합 카드를 둔다.

## 권장 문서 유형

- **통합 관리**: 최초 준비·계획에서 전체 원본, 공용 산출물, 문서 분할·소유권과 실행 순서를 정리하고 최종 검증에서 전체 누락·중복·연동을 확인한다. 개발 중 세부 진행은 기능 문서에 두며 공통 기준 변경만 예외 조정한다.
- **공통 기반/계약**: 카탈로그, 공통 상태, 저장, Provider/Fixture, 이벤트와 화면 진입 계약을 소유한다.
- **기능 문서**: 독립 사용자 흐름과 화면을 소유한다.
- **최종 통합·감사**: 문서 간 흐름과 전체 요구사항을 원본 기준으로 검수한다. 규모가 작으면 통합 관리 문서 안에 둘 수 있다.

## 소유권 규칙

- 모든 원자 요구사항은 주 소유 문서가 정확히 하나다.
- 다른 문서가 사용하는 요구사항은 소비자 또는 연동 지점으로 기록한다.
- 공통 상태·공용 Prefab·공용 서비스는 한 문서만 변경 소유권을 가진다.
- 기능 문서는 공용 허브를 직접 함께 수정하지 않고 독립 화면과 진입 계약을 제공한다.
- 문서 경계 밖 요구사항도 삭제하지 않고 다른 문서, 후속 문서 또는 클라이언트 범위 아님으로 배정한다.

## 통합 관리 문서 템플릿

[공통 문서 운영](common-document-workflow.md)에 따라 승인된 준비·검증 단계에 필요한 절만 사용한다. 개발 중에는 기능 문서의 진행 상황을 이 템플릿에 반복 복사하지 않는다.

```markdown
# {기능명} 기획서 기반 개발 통합 관리

## 원본 기준
- 모든 기획 원본: {원본별 주소·개별 버전·해시·분량·원본 간 관계}
- 직전 버전: {원본별 버전·출처}
- 기존 구현 출발 버전: {원본별 버전·출처}
- 공용 산출물: {원본별 PNG·텍스트·표 목록·대응 위치·접근 경로}

## 공통 계약 기준

## 외부 대기
```

## 실행 순서 설계

전체 문서를 완전 직렬화하지 않는다.

1. 최초 공통 준비에서 원본 전수 추출·분류를 수행하고, 각 문서는 공용 산출물을 재사용해 담당 상세 분석과 현재 구현 감사를 수행한다. 위임·병렬 실행은 승인된 문서와 작업에 한한다.
2. 공통 계약은 기능 구현이 사용할 최소 범위를 먼저 확정·통합한다.
3. 독립 화면과 Provider는 병렬 구현한다.
4. 공유 Prefab 연결과 이벤트 생산·소비는 의존 순서로 통합한다.
5. 최종 감사는 모든 문서의 완료 보고를 합산하지 않고 원본 요구사항 전체에서 다시 시작한다.

작업공간 수나 AI 수를 문서 분할 근거로 사용하지 않는다. 실행 시점의 사용 가능한 작업공간은 MindNProgress가 배정하며, 분할 구조는 기능 소유권과 검수 가능성을 기준으로 유지한다.
