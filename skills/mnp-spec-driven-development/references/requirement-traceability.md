# 요구사항 추적 규칙

## 식별자

원본 위치와 요구사항의 장기 정체성을 분리한다.

- **버전 내부 출처 ID**: `v0.3:S08-R04`, `v1.2:P12-R03`, `v5:SEC-2.1-R02`
- **안정 요구사항 ID**: 프로젝트에서 사용할 수 있으면 `REQ-{영역}-{일련번호}` 형식으로 유지한다.

작은 작업에서는 출처 ID만 사용할 수 있다. 그러나 새 버전에서 슬라이드·페이지 삽입이나 순서 이동이 발생하면 이전 ID를 덮어쓰지 말고 대응표를 기록한다. 같은 번호라는 이유로 같은 요구사항이라고 판단하지 않는다.

기획서 요구사항 외의 실행 업무도 출처가 추적돼야 한다.

- **공통 계약 ID**: `CONTRACT-{영역}-{일련번호}`
- **구현 감사 발견 ID**: `AUDIT-{영역}-{일련번호}`
- **문서 간 흐름 ID**: `XFLOW-{영역}-{일련번호}`

리팩터링·레거시 제거·공통 기반 구현처럼 특정 원자 요구사항 하나에만 대응하지 않는 카드도 위 식별자나 관련 요구사항 ID를 가진다. `기술 정리`, `공통 처리` 같은 제목만으로는 작업 출처를 대신하지 않는다.

## 원자 요구사항 기준

다음 중 하나라도 독립적으로 합격·불합격을 판단할 수 있으면 별도 요구사항으로 분리한다.

- 사용자 입력과 결과
- 상태별 표시 또는 비활성 조건
- 우선순위·정렬·랜덤·쿨다운 규칙
- 저장·재시작·일회성·소비·대기열
- 오류·순단·재시도·결과 재확인
- 화면 전환·복귀·딥링크
- 시안에만 표현된 컴포넌트·문구·화살표·팝업
- 서버·아트·사운드 계약 또는 교체 지점

넓은 화면 이름이나 기능 이름 하나를 요구사항 하나로 사용하지 않는다.

## 상태 분류

각 요구사항의 구현 수준, 검증 상태와 차단 상태를 별도로 기록한다. 부분 구현과 외부 차단처럼 동시에 성립할 수 있는 값을 하나의 상태 목록에 섞지 않는다.

### 구현 수준

- 미구현
- 부분 구현
- 더미 구현 완료
- 최종 구현 완료
- 삭제 요구사항 정리 필요
- 담당 범위 아님

### 검증 상태

- 미검증
- 자동 검증 완료
- Play 검증 완료
- 자동·Play 검증 완료
- 검증 해당 없음

### 차단 상태

- 차단 없음
- 서버 계약·데이터 대기
- 아트·애니메이션·사운드 대기
- 정책 결정 대기
- 다른 문서 구현 대기

`더미 구현 완료`는 구현 수준이며 제품 요구사항의 최종 완료 수에 포함하지 않는다. `최종 구현 완료`이면서 요구되는 검증을 마친 요구사항만 최종 완료로 집계한다. `담당 범위 아님`도 주 소유 조직·문서와 전달 기준이 확인돼야 현재 문서의 분류 완료로 인정한다.

## 추적표 스키마

| 필드 | 내용 |
|---|---|
| 안정 요구사항 ID | 버전 간 유지할 식별자 또는 생략 사유 |
| 현재 출처 ID | 최신 버전과 원본 위치 |
| 이전 출처 ID | 직전/기준 버전의 대응 위치 |
| 요구사항 | 독립 합격 판정이 가능한 문장 |
| 주 소유 문서·카드 | 정확히 하나 |
| 소비·연동 문서 | 필요한 경우 복수 |
| 변경 분류 | 추가/변경/유지/삭제/정책 미정 |
| 구현 수준 | 미구현/부분 구현/더미 구현 완료/최종 구현 완료/삭제 정리 필요/담당 범위 아님 |
| 검증 상태 | 미검증/자동 완료/Play 완료/자동·Play 완료/해당 없음 |
| 차단 상태 | 없음/서버/리소스/정책/다른 문서 |
| 구현 근거 | 현재 통합 기준 파일·클래스·메서드·Prefab·커밋 |
| 자동 검증 | 테스트 이름, 조건, 실제 결과 |
| Play 증거 | 진입 경로, 상태, 해상도, 실제 결과·캡처 |
| 잔여 작업 | 정확한 미완료 범위 |
| 대기·재개 조건 | 필요한 계약·정책·에셋과 재개 기준 |

`기존 코드에 있을 것 같다`, `이전 카드가 완료다`, `컴파일된다`는 단독 구현 근거가 아니다.

## 버전 차이 분석

두 관점을 분리한다.

1. **기존 구현 출발 버전 → 최신 버전**: 오래된 구현이 최신 요구와 얼마나 다른지 확인한다.
2. **직전 버전 → 최신 버전**: 이번 변경으로 재개할 카드·테스트를 결정한다.

각 변경은 요구사항 추가, 의미 변경, 상태·예외 추가, 위치만 이동, 삭제, 판단 불가로 분류한다. 삭제는 추적표에서 지우지 않고 기존 동작·데이터·UI 제거 또는 비활성화 필요 여부를 기록한다.

## 커버리지 불변조건

- 최신 원본의 모든 슬라이드·페이지·절이 계수된다.
- 모든 요구사항은 주 소유 문서가 정확히 하나다.
- 통합 관리 문서의 전역 소유권 원장을 소유권 판정의 단일 기준으로 사용한다.
- 공통 문서나 소비 문서에 같은 요구사항을 설명용으로 복제할 수는 있지만, 각 사본에 `주 소유/소비/참고` 역할을 표시하고 `주 소유`는 정확히 하나만 둔다. 여러 문서에 같은 ID가 있다는 사실만으로 공동 소유를 허용하지 않는다.
- 모든 구현 카드는 하나 이상의 요구사항 ID, 공통 계약 ID, 구현 감사 발견 ID 또는 문서 간 흐름 ID를 가진다.
- 요구사항 없는 원본 단위도 `요구사항 없음/참고 시안`으로 남는다.
- 최종 완료 요구사항은 `최종 구현 완료`이고 구현 근거와 요구되는 자동/Play 검증 증거가 있다.
- 더미 구현 완료와 최종 구현 완료를 별도로 집계한다.
- 외부 차단은 전달물과 재개 조건이 있다.
- 미분류·미검증 수는 완료 시 0이다.

## 기계 검사가 가능한 최소 필드

자동 점검을 도입할 수 있도록 통합 원장과 실행 카드에는 다음 값을 일관된 표기나 구조화 필드로 남긴다.

- 식별자
- 소유 역할: `주 소유/소비/참고`
- 주 소유 문서·카드 ID
- 구현 수준
- 검증 상태
- 차단 상태
- 요구되는 검증 종류: `자동/Play/둘 다/해당 없음`
- 외부 대기 여부와 재개 조건

자연어 본문에만 흩어진 소유권과 상태는 사람이 읽을 수 있어도 전역 중복·누락 검사를 안정적으로 수행할 수 없다.

## 종료 수치

최소 다음 수치를 문서별·전체로 집계한다.

- 전체 원자 요구사항
- 더미 구현 완료
- 최종 구현 완료
- 부분 구현
- 미구현
- 자동 검증 완료
- Play 검증 완료
- 서버/리소스 차단
- 정책 미정
- 담당 범위 아님
- 미분류·미검증

분모와 상태가 다른 수치를 하나의 진행률로 압축하지 않는다.
