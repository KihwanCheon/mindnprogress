# 회귀 평가 규칙과 기준 사례

## 목적

기획서 기반 개발 절차를 바꾼 뒤에는 카드가 많아졌다는 사실이 아니라, 과거에 발생한 누락과 성급한 완료 판정을 새 절차가 실제로 차단하는지 평가한다. 평가는 라이브 문서를 수정하지 않는 읽기 전용 스냅샷으로 수행하고, 문서 버전과 평가 시각을 남긴다.

## 평가 방법

1. 실패가 확인된 과거 문서와 당시 원본 버전을 기준선으로 고정한다.
2. 최신 원본의 페이지 수, 삽입·삭제·이동과 시각 전용 요구사항을 다시 확인한다.
3. 새 분할 문서 전체를 한 묶음으로 조회한다.
4. 아래 불변조건을 과거와 현재에 동일하게 적용한다.
5. 발견한 구조적 공백만 스킬·템플릿·자동 점검 후보로 반영한다.

## 평가 불변조건

| 구분 | 판정 질문 |
|---|---|
| 원본 기준 | 최신·직전·구현 출발 버전과 전체 원본 단위가 식별됐는가? |
| 전수 분석 | 담당 원본, 장기 차이, 직전 변경 영향, 현재 구현 감사가 분리됐는가? |
| 원자 추적 | 독립 합격 가능한 요구사항 ID와 상태가 있는가? |
| 전역 소유권 | 요구사항마다 전역 원장에서 주 소유 문서가 정확히 하나인가? |
| 실행 출처 | 모든 구현 카드가 요구사항·계약·감사 발견·문서 간 흐름 ID를 가지는가? |
| 정책 전파 | 필요한 하위 카드에 정책 Ref가 올바른 방향으로 연결됐는가? |
| 외부 경계 | 더미 완료와 서버·아트·사운드·정책 후속이 분리됐는가? |
| 독립 검수 | 자동 검증과 최신 통합 Play, 요구사항 전수 감사가 구분됐는가? |
| 집계 정합 | 업무를 가진 루트·묶음 카드가 직접 업무로 중복 집계되지 않는가? |
| 종료 판정 | 상태별 수치와 미분류·미검증 0을 확인하는가? |

카드 수와 요구사항 수는 누락을 탐지하는 경보로 사용하되 고정 합격선으로 사용하지 않는다. 원본의 정보 밀도와 분할 경계에 따라 적정 수가 달라진다.

## 기준 사례: JP-매니저 v0.2 실패와 v0.3 분할 절차

평가 스냅샷: 2026-09-05. 이후 라이브 문서는 변경될 수 있다.

### 원본

- v0.2: 48장
- v0.3: 49장
- v0.3은 로비 진입 발화 기본 규칙 슬라이드가 추가됐고 이후 대응 슬라이드 번호가 이동했다. 번호가 아니라 내용 기준 대응이 필요하다.

### 구조 지표

| 지표 | v0.2 단일 문서 | v0.3 분할 문서 8개 |
|---|---:|---:|
| MnP 카드 | 9 | 184 |
| 실제 업무 카드 | 5 | 133 |
| 원자 요구사항 ID | 0 | 서로 다른 ID 247종 |
| 정책 Ref | 0 | 각 문서 1개씩 8개 |
| 지식선 | 0 | 다수의 분석·정책·구현 근거 연결 |

v0.2 문서는 대표 더미 구현과 Play 카드로 수직 단면을 검증했지만, 48장 전체의 요구사항 소유권과 상태를 추적하지 않았다. 따라서 결과 자체는 재사용 후보가 될 수 있어도 전체 기획 완료 근거가 될 수 없다.

v0.3 분할 문서는 공통 기반/계약, 획득/로비, 관리/변경, 선물하기, 스토리, 옷장, 보이스, Q&A로 나뉘었고 대부분 담당 원본 분석, v0.1→v0.3 차이, v0.2→v0.3 영향, 현재 구현 감사, 더미 구현, 후속 연동, 자동·Play·전수 검수 구조를 가진다. 모든 문서에서 더미 UI 시안 정합 Ref도 확인됐다. 이는 v0.2의 대표 단면 오판을 구조적으로 크게 줄인다.

### 회귀 평가에서 남은 공백

1. **전역 주 소유권이 기계 판정 가능하지 않다.** 공통 문서와 기능 문서에 같은 `Sx-Ry` ID가 설명용으로 함께 등장한다. 평가 시 247종 중 100종이 둘 이상의 문서에 나타났다. 이것이 참고 복제인지 공동 소유인지 자연어만으로는 안정적으로 구분할 수 없다.
2. **기획 외 실행 업무의 출처 ID가 없다.** 공통 계약 구현과 감사 파생 레거시 제거처럼 정당한 작업도 요구사항 ID 없이 존재한다. 각각 `CONTRACT-*`, `AUDIT-*`처럼 출처를 명시해야 “근거 없는 범위 확장”과 구분할 수 있다.
3. **집계 루트 규칙이 일부 문서에서 일관되지 않다.** 평가 당시 스토리·옷장·Q&A 루트가 하위 업무를 가지면서 `isWork=true`였다. 루트 진행률과 실제 업무가 중복 집계될 여지를 없애야 한다.
4. **통합 관리 원장이 평가 대상 8개 문서 안에서 단일 기준으로 드러나지 않는다.** 문서별 분석이 좋아도 전체 누락·중복·교차 흐름은 별도 전역 원장과 최종 감사가 필요하다.

### 이 사례로 확정한 스킬 보강

- 반복 정책을 위한 Ref 카드 템플릿과 연결 게이트를 제공한다.
- 전역 소유권 원장을 단일 기준으로 삼고 각 요구사항 사본에 `주 소유/소비/참고` 역할을 표시한다.
- 구현 카드의 허용 출처를 요구사항, 공통 계약, 감사 발견, 문서 간 흐름 ID로 명시한다.
- 하위 업무가 있는 루트·묶음 카드는 집계 전용으로 두는 규칙을 회귀 점검 항목에 포함한다.

## 자동화 후보

다음 검사는 MindNProgress 문서 조회만으로 반복 가능하므로 자동화 우선순위가 높다.

1. 전체 원본 단위 계수와 담당 문서 누락 검사
2. 요구사항별 주 소유 0개·2개 이상 검사
3. 구현 카드의 요구사항·계약·감사·흐름 ID 누락 검사
4. 적용 대상 UI 카드의 필수 정책 Ref 지식선 누락·방향·정책 검사
5. 하위 업무가 있는 루트·묶음 카드의 `isWork=true` 검사
6. 완료 요구사항의 구현 근거·필수 자동/Play 증거 누락 검사
7. 외부 차단 항목의 전달물·재개 조건 누락 검사

자동 검사는 완료 판정을 대신하지 않는다. 이상 후보를 제시하고, 최종 판정은 원본과 최신 통합 결과를 확인한 독립 검수가 수행한다.
