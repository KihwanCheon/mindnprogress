# 실패 유형과 방지 규칙

## 대표 단면을 전체 완료로 판정

**징후**

- 기획 분량에 비해 카드와 요구사항 수가 지나치게 작다.
- 주요 화면 몇 개와 넓은 체크리스트만 완료됐다.

**방지**

- 모든 원본 단위를 계수하고 원자 요구사항 추적표를 완료 게이트로 사용한다.
- 대표 프로토타입 완료와 전체 기획 완료를 별도 상태로 보고한다.

## 텍스트 요약 과정에서 시각 요구사항 누락

**징후**

- 이미지에만 있는 버튼 상태, 화살표, 팝업과 레이아웃이 카드에 없다.

**방지**

- PPTX·PDF 렌더링 이미지를 직접 확인한다.
- 시안 상태를 요구사항으로 등록하고 Play 결과와 직접 대조한다.

## 기존 코드와 과거 완료 상태를 자동 신뢰

**징후**

- `기존 코드에 있음`, 과거 커밋 또는 `done/100%`만 구현 근거로 적혀 있다.

**방지**

- 현재 통합 기준의 파일·Prefab 존재, 최신 요구와의 일치, 컴파일과 관련 테스트를 다시 확인한다.
- 기존 결과는 그대로 사용/수정 사용/교체/제거/구현 없음으로 감사한다.

## 외부 의존 항목이 사라짐

**징후**

- 서버·아트·정책이 미정이라는 이유로 요구사항과 카드가 없다.

**방지**

- 더미 완료와 실제 연동을 분리한다.
- 요구사항 상태, 대기 전달물, 임시값, 교체 지점과 재개 조건을 유지한다.

## 하위 실행자의 diff만 검수

**징후**

- 변경 파일은 정상이나 기존 코드에 남은 미구현 요구사항을 확인하지 않았다.

**방지**

- 변경 품질 검수와 요구사항 전수 검수를 분리한다.
- 독립 검수자는 최신 원본과 추적표에서 시작한다.

## 문서 분할 후 소유권 누락·중복

**징후**

- 어느 문서도 담당하지 않는 원본 항목이 있다.
- 여러 기능 담당자가 같은 공통 상태·Prefab을 수정한다.

**방지**

- 모든 요구사항에 정확히 하나의 주 소유 문서를 둔다.
- 공통 계약과 소비자를 구분하고 통합 관리 문서에서 전체 커버리지를 검사한다.

## 루트 지침이 하위 카드까지 전달되지 않음

**징후**

- 루트에는 시안 정합 요구가 있지만 하위 제작 카드와 위임 전문에는 없다.

**방지**

- 정책을 독립 지식 카드로 만들고 적용 대상 하위 카드에 `reuse-first`로 연결한다.
- 하위 카드의 설명·체크리스트에 관찰 가능한 완료 조건을 둔다.

## 과거 Play 결과를 최신 증거로 사용

**징후**

- 기획·Prefab·데이터가 바뀌었는데 이전 캡처와 테스트만 인용한다.

**방지**

- 변경 영향 요구사항의 자동 테스트와 Play 검증을 재개한다.
- 과거 결과는 비교 기준으로만 사용한다.

## 슬라이드 번호 이동을 요구사항 변경으로 오판

**징후**

- 중간 슬라이드 삽입 후 이후 모든 요구사항이 새 항목으로 분류되거나 잘못 대응된다.

**방지**

- 버전과 원본 위치를 포함한 출처 ID를 사용한다.
- 번호뿐 아니라 요구 내용, 표 구조와 시안을 비교하고 이전→현재 대응표를 만든다.

## 루트 진행률과 실제 완성도 불일치

**징후**

- 분석 일부만 끝났는데 루트가 100%다.
- 기존 업무의 진행률이 최신 재정비 완료로 해석된다.

**방지**

- 집계 루트는 실제 하위 업무 결과에서 진행률이 파생되도록 구성한다.
- 버전 재정비와 기존 작업 진행률을 구분하고 완료 수치표를 함께 보고한다.

## 과잉 구현·요구사항 승격·준비 순환

위 유형들이 누락·과소 구현을 다루는 것과 반대로, 원본에 없는 범위가 커지거나 준비·검수만 반복되는 실패다.

**징후**

- 원본의 미결정 문구(예: `가능한지 확인 필요`)나 AI가 작성한 계약·결정 기록·검수 체크리스트가 구현 범위와 완료 조건으로 바뀌어 큰 코드가 생긴다.
- 계약 준비 → 부분 구현 → 독립 검수 → 입력 부족 반환 → 계약 보완이 반복되고, 사용자가 새로 확인할 수 있는 동작은 늘지 않는다.
- 위임·검수 횟수와 문서·카드 갱신은 많지만 담당 요구사항의 구현 수준과 검증 상태가 바뀌지 않는다.

사례: 2026-10 한 상점 더미 제작 문서에서 6일 동안 준비·검수 순환이 이어졌고, 원본의 `가능한지 확인 필요` 문구 하나가 약 9.3천 줄 구현으로 확대됐다. 사용자가 여러 대화에 위임 중지를 직접 지시해야 했다.

**방지**

- 요구사항과 완료 조건의 근거는 기획 원본과 사용자 결정만 인정한다. AI가 작성한 계약·결정 기록·검수 체크리스트와 하위 제안은 설계 자료이며, 요구사항이나 완료 조건으로 자동 채택하지 않는다.
- 원본의 미결정·확인 필요 항목은 `정책 결정 대기`로 분류하고 결정 요청으로 보고한다. 임시값이 필요하면 범위와 교체 지점을 기록한 최소 더미로 제한한다.
- 위임 전문에는 [위임·지시 전문 작성](delegation-and-validation.md#위임지시-전문-작성)에 따라 이번 위임 후 사용자가 새로 확인할 수 있는 동작과 담당 요구사항 ID를 적는다.

**중단 기준**

- 같은 목표·카드에 대한 연속 2회 위임에서 담당 요구사항의 구현 수준이나 검증 상태가 하나도 진척되지 않으면(문서·계약·체크리스트 갱신만 있으면) 다음 재위임을 멈춘다. 반복 원인, 현재 상태, 선택지를 사용자에게 보고하고 진행 방향을 다시 확인받는다.
- 반복 횟수만으로 미해결 문제를 완료 처리하지 않는다.

## 감사 질문

이전 결과를 복구할 때 다음 질문에 하나라도 답할 수 없으면 완료를 재판정한다.

1. 최신 원본의 모든 단위가 어디에 계수됐는가?
2. 각 요구사항의 주 소유 문서는 어디인가?
3. 현재 통합 코드의 구현 근거는 무엇인가?
4. 최신 버전에서 다시 실행한 테스트와 Play 증거는 무엇인가?
5. 부분 구현과 외부 차단은 완료에서 제외됐는가?
6. 삭제·변경된 과거 동작이 남아 있지 않은가?
7. 하위 UI 카드가 시안 정합 지식을 실제로 사용했는가?
8. 미분류·미검증 요구사항이 0개인가?
9. 구현된 범위와 완료 조건이 모두 원본이나 사용자 결정에 근거하며, 최근 위임들이 담당 요구사항의 상태를 실제로 진척시켰는가?
