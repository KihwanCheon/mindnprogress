## 1. 실행 컨텍스트 확인

MCP 조회 결과의 `guide`, `selection.taskLinks.startupInspection`, `selection.aiWorkCoordination`, `nextStep`을 따르세요. 그룹 소속이면 `mindnprogress_get_group_context`로 최신 기준과 승인 범위를 확인하세요. 작업공간에 `AGENTS.md`·`CLAUDE.md`가 있으면 먼저 읽고 그 개발 지침·구조를 따르세요. AionUi와의 협업을 기본으로 하며, 필요한 스킬·커맨드는 AionUi와 현재 AI 에이전트에서 가져와 활용하세요.

관련 카드를 수정하기 전에는 AI 작업 상태를 확인하세요.

- 선택 카드 밖의 형제·하위·선행 카드를 수정하려면 `mindnprogress_get_ai_work_states`를 호출하고, `running`·`waiting-confirmation` 카드는 사용자 지시 없이 동시에 수정하지 않습니다.
- 작업공간·worker는 임의로 선택하지 말고 필요하면 `mindnprogress_get_ai_workspace_pool`로 확인합니다.
- MCP 도구를 사용할 수 없거나 문서·카드를 찾지 못하면 추측하지 말고 확인 가능한 범위만 보고합니다.

지식선은 이번 작업에서 실제로 조회하고 근거로 사용한 카드에만 연결하세요. 제목이 비슷하거나 주제가 같다는 이유만으로 연결하지 않습니다.

## 2. 기록 원칙

실제로 승인된 작업을 수행했을 때만 결과를 기록하세요.

- 댓글은 `[진행]`·`[차단]`·`[결과]` 중 하나로 시작하는 1~2문장 요약과 필요한 상세로 작성합니다.
- 진행 과정·도구 로그는 댓글에, 다른 카드나 후속 세션이 재사용할 사실·결정·제약·검증 결과만 `sharedKnowledge`에 남깁니다. 진행 로그·중복·폐기된 결론은 넣지 않습니다.
- 외부 전달물이나 결정 대기는 제목이 아니라 `waitingItems`로 기록합니다. 막히면 `[차단]`과 재개 조건을, 해결되면 `[진행]`과 함께 대기 항목 해제를 남깁니다.
- 카드 일부만 바꿀 때는 변경 필드만 전송합니다. `description`·`sharedKnowledge` 일부 수정은 조회한 text integrity 해시를 쓰고, 같은 필드 수정은 순차 처리합니다.
- 변경 후에는 최신 문서·카드를 다시 조회해 결과를 검증합니다.

## 3. 작업 분류와 개발 절차

작업을 개발·코드 변경 / 분석·설계 / 검토·검증 / 문서·운영 중 하나로 분류하세요. 개발·코드 변경에는 아래 SDD·TidyFirst·TDD·병렬 개발 절차를 기본 적용하고, 다른 유형은 필요할 때만 적용하며 코드 변경이 없으면 강제하지 않습니다.

### SDD

구현 전에 목표·범위, 추적 가능한 요구사항, 입력·출력 계약, 불변조건, 오류·실패·보류 흐름, 멱등성·재시도 규칙, 수용 기준, 완료 조건, 제외 범위와 남은 위험을 확정하고 이를 구현·테스트·리뷰의 기준으로 삼으세요.

### TidyFirst

동작을 바꾸기 전에 필요한 구조 정리(이름·중복·배치)가 있으면 먼저 작은 정리로 분리해 커밋하고, 그다음 동작 변경을 별도로 진행하세요. 정리와 동작 변경을 한 커밋에 섞지 않습니다.

### TDD

코드 동작을 바꾸는 작업은 TDD를 우선합니다: 정상·경계값·오염·시점·실패·회귀 테스트를 정의하고, 필요하면 실패하는 테스트를 먼저 작성한 뒤 통과시키는 최소 구현을 하고, 통과 후 리팩터링하며, 기존 동작 보존을 별도로 검증합니다. 레거시 구조·설정 변경·순수 UI 작업 등 테스트 우선이 부적절하면 이유와 대체 검증 방법을 남기세요.

### 병렬 개발과 worktree

독립적인 개발 스트림이 둘 이상이거나 장기 작업이면 역할이 명확한 서브에이전트에 병렬 위임하세요. 각 작업은 별도 worktree와 짧은 기능 브랜치를 생성해 병렬 작업하고, 경로는 현재 작업공간 안내와 저장소 규칙을 따르며 임의로 추측하지 않습니다. 소유 파일이 겹치지 않게 하고, 같은 worktree에서 병렬 쓰기를 하지 않으며, 결합도가 높거나 같은 파일을 수정하는 작업은 순차 처리합니다. worktree·worker 선택은 MindNProgress에 등록된 작업공간 기준을 따르고, 단순하고 짧은 단일 작업에는 병렬화를 억지로 적용하지 않습니다.

### 기능 단위 커밋

각 기능은 관련 스펙·테스트·구현·검증을 포함하는 하나의 검증 가능한 단위로 커밋하세요. 무관한 변경을 섞지 말고, 커밋 전에 관련 테스트·검증 명령을 실행하며, 결과에는 변경 범위·파일·검증 명령과 결과·미검증 위험을 남깁니다. 통합은 별도 `integrator`가 clean 상태·충돌·커밋 범위·전체 회귀 테스트·worktree 정리를 확인합니다. push·배포는 별도 승인 없이 하지 않습니다.
