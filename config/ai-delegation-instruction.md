## 1. 실행 컨텍스트와 MindNProgress 확인

MCP 조회 결과의 `guide`, `selection.taskLinks.startupInspection`, `selection.aiWorkCoordination`, `nextStep`을 확인하고 따르세요. 그룹 소속이면 `mindnprogress_get_group_context`로 최신 기준과 두 단계 사용자 승인 범위를 확인하세요.

관련 카드를 수정하기 전에는 AI 작업 상태를 확인하세요.

- 선택 카드 밖의 형제·하위·선행 카드를 수정해야 하면 `mindnprogress_get_ai_work_states`를 호출합니다.
- `running` 또는 `waiting-confirmation` 상태의 카드는 사용자 지시 없이 동시에 수정하지 않습니다.
- 등록된 작업공간이나 worker를 임의로 선택하지 않습니다. 필요하면 `mindnprogress_get_ai_workspace_pool`로 최신 목록과 상태를 확인합니다.
- MCP 도구를 사용할 수 없거나 문서·카드를 찾지 못하면 추측하지 말고 확인 가능한 범위와 제약만 보고합니다.

지식선은 이번 작업에서 실제로 조회하고 근거로 사용한 카드에 대해서만 판단하세요. 제목이 비슷하거나 같은 주제라는 이유만으로 연결하지 않습니다.

## 2. 승인된 작업의 기록 원칙

실제로 승인된 작업을 수행한 경우에만 결과를 기록하세요.

- 댓글은 `[진행]`, `[차단]`, `[결과]` 중 하나로 시작하는 1~2문장의 요약과 필요한 상세 내용으로 작성합니다.
- 진행 과정과 도구 로그는 댓글에 기록하고, 다른 카드나 후속 세션에서 재사용할 사실·결정·제약·검증 결과만 `sharedKnowledge`에 기록합니다.
- `sharedKnowledge`에 진행 로그, 중복 내용, 폐기된 결론을 복사하지 않습니다.
- 외부 전달물이나 결정 대기는 제목이 아니라 `waitingItems`로 기록합니다.
- 작업이 막히면 `[차단]` 댓글과 재개 조건을 남기고, 해결되면 `[진행]` 댓글과 함께 대기 항목을 해제합니다.
- 카드 일부를 수정할 때는 전체 카드 데이터를 재전송하지 말고 변경 필드만 전송합니다.
- `description` 또는 `sharedKnowledge` 일부를 수정할 때는 조회된 text integrity 해시를 사용하고, 같은 필드의 수정은 반드시 순차 처리합니다.
- 변경 후에는 최신 문서 또는 카드를 다시 조회해 실제 결과를 검증합니다.

## 3. 작업 분류와 개발 절차

작업을 먼저 다음 중 하나로 분류하세요.

- 개발·코드 변경
- 분석·설계
- 검토·검증
- 문서·운영

개발·코드 변경 작업에는 아래 SDD·TDD·병렬 개발 절차를 기본 적용합니다. 분석·설계·검토·문서·운영 작업에는 필요한 경우에만 적용하며, 코드 변경이 없으면 SDD·TDD·worktree·기능 단위 커밋을 강제하지 않습니다.

### SDD

구현 전에 목표와 범위, 기능 ID 또는 추적 가능한 요구사항, 입력·출력 계약, 도메인 불변조건, 오류·실패·보류 흐름, 멱등성 및 재시도 규칙, 수용 기준, 완료 조건, 제외 범위와 남은 위험을 확정하세요. 승인된 스펙을 구현·테스트·리뷰의 기준으로 사용하세요.

### TDD

코드 동작을 변경하는 작업은 TDD를 우선합니다.

1. 정상 동작 테스트를 정의합니다.
2. 경계값·오염·시점·실패·회귀 테스트를 정의합니다.
3. 필요한 경우 실패하는 테스트를 먼저 작성합니다.
4. 테스트를 통과시키는 최소 구현을 합니다.
5. 테스트 통과 후 리팩터링합니다.
6. 기존 동작 보존 여부를 별도로 검증합니다.

레거시 구조, 설정 변경, 순수 UI 작업 또는 테스트 우선 접근이 부적절한 경우에는 그 이유와 대체 검증 방법을 결과에 남기세요.

### 병렬 개발과 worktree

서로 독립적인 개발 스트림이 둘 이상이거나 작업이 장시간 진행되면 역할이 명확한 서브에이전트에 병렬 위임하세요.

- 독립적인 개발 스트림이나 장기 작업은 별도 worktree와 짧은 기능 브랜치를 생성해 병렬 작업하세요. 구체적인 경로는 현재 작업공간 안내와 저장소 규칙을 따르고 임의로 추측하지 않습니다.
- 각 작업은 짧은 기능 브랜치를 사용합니다.
- 병렬 작업 간 소유 파일이 겹치지 않게 합니다.
- 같은 worktree에서 병렬 쓰기를 하지 않습니다.
- 결합도가 높거나 같은 파일을 수정하는 작업은 순차 처리합니다.
- worktree와 worker 선택은 MindNProgress에 등록된 작업공간 기준을 따릅니다.
- 단순하고 짧은 단일 작업에는 병렬화와 worktree를 억지로 적용하지 않습니다.

### 기능 단위 커밋

각 기능은 관련 스펙·테스트·구현·검증을 포함하는 하나의 검증 가능한 기능 단위로 커밋하세요.

- 서로 무관한 변경을 하나의 커밋에 섞지 않습니다.
- 커밋 전에 관련 테스트와 검증 명령을 실행합니다.
- 커밋 결과에는 기능 범위, 변경 파일, 검증 명령, 결과와 미검증 위험을 남깁니다.
- 통합은 별도 `integrator`가 담당합니다.
- `integrator`는 clean 상태, 충돌, 커밋 범위, 전체 회귀 테스트와 worktree 정리를 확인합니다.
- push·배포는 별도 승인이 없으면 수행하지 않습니다.

## 4. 개발 도구

개발 도구는 mise 기준으로 사용하세요.

1. 저장소의 `mise.toml`, `.mise.toml`, `.tool-versions`와 현재 툴체인을 확인합니다.
2. 필요한 도구나 버전이 이미 설치되어 있는지 확인합니다.
3. 누락된 경우에만 필요한 범위의 `mise install`을 수행합니다.
4. 불필요한 전체 설치나 장시간 설치는 피합니다.
5. 실제 실행 명령과 검증 결과를 보고합니다.
