# 회귀 평가 규칙과 기준 사례

## 목적

기획서 기반 개발 절차를 바꾼 뒤에는 카드가 많아졌다는 사실이 아니라, 과거에 발생한 누락과 성급한 완료 판정을 새 절차가 실제로 차단하는지 평가한다. 평가는 라이브 문서를 수정하지 않는 읽기 전용 스냅샷으로 수행하고, 문서 버전과 평가 시각을 남긴다.

## 평가 방법

1. 실패가 확인된 과거 문서와 당시 원본 버전을 기준선으로 고정한다.
2. 최신 원본의 페이지 수, 삽입·삭제·이동과 시각 전용 요구사항을 다시 확인한다.
3. 새 분할 문서 전체를 한 묶음으로 조회한다.
4. 아래 불변조건을 과거와 현재에 동일하게 적용한다.
5. 발견한 구조적 공백만 스킬·템플릿·자동 점검 후보로 반영한다.

### 지침 개정의 행동 회귀

스킬·지침을 줄이거나 재구성할 때는 문구 일치나 문자 수가 아니라 대표 시나리오에서의 행동으로 판정한다. 최소 시나리오는 승인 경계(분석 승인만 있을 때 실행하지 않음), 위임 대상 선택(기존 하위 카드에 위임), 결과 보고 작성과 수신·인수, 완료 판정(더미·외부 대기 카드)이다.

- 같은 의미의 중복 문장만 제거한다. 축약으로 규칙의 조건·예외·이유가 사라지면 회귀로 본다.
- 2026-10-01 MindNProgress 지침 경량화는 문구 고정 테스트만 통과한 채 행동 계약이 빠져 전체 롤백됐다(`C:/Git/MindNProgress/MindNProgress/docs/ai-guidance-rollback-2026-10-01`). 같은 유형을 막기 위해 개정 전후에 위 시나리오를 같은 조건으로 비교한다.

### 단계 실행과 외부 의존 분리 시나리오

다음은 지침 개정 전후를 대조할 대표 입력과 기대 행동이다. 라이브 카드 변경 없이 같은 조건으로 검토하고, 실제 실행 시험을 하지 않았다면 지침 대조 결과와 구분해 보고한다.

| 입력 상황 | 기대 행동 |
|---|---|
| 내부 구현·검증은 통과했고 외부 API 전달만 대기, 카드 분리 승인 있음 | 후속 카드에 원래 요구사항·남은 조건·전달물·재개 조건을 저장·재조회한 뒤 원카드 범위를 정리해 완료한다. 후속·문서·제품은 미완료로 남긴다. |
| 내부 구현 결함 또는 수행 가능한 필수 Play 검증이 남음 | 외부 대기 카드로 옮겨 원카드를 완료하지 않는다. 현재 범위의 보완·검증을 계속한다. |
| 분석 승인만 있거나 새 후속 카드 생성·범위 재배정 승인이 없음 | 분리안을 제시하고 필요한 범위의 승인을 요청한다. 기존 승인에 분리가 포함돼 있으면 다시 묻지 않는다. |
| 같은 외부 업무의 후속 카드가 이미 존재함 | 기존 카드를 재사용한다. 원래 요구사항의 주 소유권과 완료 수를 중복시키지 않는다. |
| 후속 저장 실패·저장 결과 미확인 | 원카드의 범위·체크리스트·대기를 보존하고 완료하지 않는다. |
| 후속 카드 저장·확인 후 원카드 체크리스트를 정리하면 자동 완료됨 | 이 정리를 완료 저장으로 취급하고 사전에 원카드의 나머지 구현·검증을 확인한다. 저장 후 양쪽 카드 상태·대기를 재조회한다. |
| 다음 단계가 외부 전달물에 의존함 / 무관한 승인된 단계가 있음 | 필요한 단계의 대기는 유지한다. 무관한 단계는 현재 단계 인수 후 진행한다. 분리만으로 외부 입력이 준비됐다고 판단하지 않는다. |
| 같은 단계의 독립 카드가 둘임 / 문서 전체의 여러 단계가 미완료임 | 소유권·선행 조건이 분리된 같은 단계 업무는 병렬화할 수 있다. 여러 단계를 한꺼번에 열어 각 단계의 검증·인수를 미루지 않는다. |
| 현재 기준으로 인수한 카드에 변경 없음 / 실제 결함·요구사항 변경 발견 | 변경 없으면 완료를 유지한다. 결함·변경은 근거와 영향 범위를 식별해 해당 카드·검증을 재개한다. 최종 전수 감사는 생략하지 않는다. |
| 단계 중 체크리스트 일부만 검증 완료 | 하위 실행자가 실제 완료분을 반영한다. 단계 끝까지 진행률을 고정하거나 루트 진행률을 직접 바꾸지 않는다. |
| 같은 목표·카드의 연속 2회 위임이 문서 보완만 하고 무진척 | 다음 재위임을 멈추고 원인·상태·선택지를 보고해 방향을 재확인한다. 카드 분리·이름 변경으로 같은 미완료 목표의 반복을 숨기지 않는다. |

## 평가 불변조건

| 구분 | 판정 질문 |
|---|---|
| 원본 기준 | 최신·직전·구현 출발 버전과 전체 원본 단위가 식별됐는가? |
| 전수 분석 | 담당 원본, 장기 차이, 직전 변경 영향, 현재 구현 감사가 분리됐는가? |
| 원자 추적 | 독립 합격 가능한 요구사항 ID와 상태가 있는가? |
| 전역 소유권 | 요구사항마다 전역 원장에서 주 소유 문서가 정확히 하나인가? |
| 실행 출처 | 모든 구현 카드가 요구사항·계약·감사 발견·문서 간 흐름 ID를 가지는가? |
| 정책 전파 | 필요한 하위 카드에 정책 Ref가 올바른 방향으로 연결됐는가? |
| 외부 경계 | 더미 완료와 서버·아트·사운드·정책 후속이 분리됐는가? 원카드 완료 전에 후속 업무의 저장·대기·소유권을 확인했는가? |
| 단계 진행 | 현재 단계의 구현·검증·인수 후 다음 단계로 이동하며, 완료 범위의 재개에는 실제 변경·결함 근거가 있는가? |
| 독립 검수 | 자동 검증과 최신 통합 Play, 요구사항 전수 감사가 구분됐는가? |
| 집계 정합 | 업무를 가진 루트·묶음 카드가 직접 업무로 중복 집계되지 않는가? |
| 종료 판정 | 상태별 수치와 미분류·미검증 0을 확인하는가? |
| 수행 주체 | 상위 담당자가 기존 하위 업무를 직접 실행·기록하지 않고 해당 카드에 위임했는가? |
| 지시·위임 상태 분리 | 그룹 지시 상태(`queued`~`expired`), 위임·보고 상태와 업무 완료를 구분했는가? |
| 보고 판정 연결 | 보고가 요구사항 ID별 상태·검증자·접근 가능한 영속 근거를 연결하고, 수신 확인·근거 검수·결과 인수를 구분했는가? 결과 절단 가능성을 확인했는가? |
| 범위 유지 | 요구사항과 완료 조건이 원본·사용자 결정에서만 나왔고, 연속 2회 무진척 위임에서 중단·재확인했는가? |
| 서버 상태 정합 | 체크리스트 전체 체크나 `done/100` 저장으로 대기가 남은 카드가 완료되거나 `waitingItems`가 사라지지 않았는가? |

카드 수와 요구사항 수는 누락을 탐지하는 경보로 사용하되 고정 합격선으로 사용하지 않는다. 원본의 정보 밀도와 분할 경계에 따라 적정 수가 달라진다.

## 기준 사례: JP-매니저 v0.2 실패와 v0.3 분할 절차

평가 스냅샷: 2026-09-05. 이후 라이브 문서는 변경될 수 있다.

### 원본

- v0.2: 48장
- v0.3: 49장
- v0.3은 로비 진입 발화 기본 규칙 슬라이드가 추가됐고 이후 대응 슬라이드 번호가 이동했다. 번호가 아니라 내용 기준 대응이 필요하다.

### 구조 지표

| 지표 | v0.2 단일 문서 | v0.3 분할 문서 8개 |
|---|---:|---:|
| MnP 카드 | 9 | 184 |
| 실제 업무 카드 | 5 | 133 |
| 원자 요구사항 ID | 0 | 서로 다른 ID 247종 |
| 정책 Ref | 0 | 각 문서 1개씩 8개 |
| 지식선 | 0 | 다수의 분석·정책·구현 근거 연결 |

v0.2 문서는 대표 더미 구현과 Play 카드로 수직 단면을 검증했지만, 48장 전체의 요구사항 소유권과 상태를 추적하지 않았다. 따라서 결과 자체는 재사용 후보가 될 수 있어도 전체 기획 완료 근거가 될 수 없다.

v0.3 분할 문서는 공통 기반/계약, 획득/로비, 관리/변경, 선물하기, 스토리, 옷장, 보이스, Q&A로 나뉘었고 대부분 담당 원본 분석, v0.1→v0.3 차이, v0.2→v0.3 영향, 현재 구현 감사, 더미 구현, 후속 연동, 자동·Play·전수 검수 구조를 가진다. 모든 문서에서 더미 UI 시안 정합 Ref도 확인됐다. 이는 v0.2의 대표 단면 오판을 구조적으로 크게 줄인다.

### 회귀 평가에서 남은 공백

1. **전역 주 소유권이 기계 판정 가능하지 않다.** 공통 문서와 기능 문서에 같은 `Sx-Ry` ID가 설명용으로 함께 등장한다. 평가 시 247종 중 100종이 둘 이상의 문서에 나타났다. 이것이 참고 복제인지 공동 소유인지 자연어만으로는 안정적으로 구분할 수 없다.
2. **기획 외 실행 업무의 출처 ID가 없다.** 공통 계약 구현과 감사 파생 레거시 제거처럼 정당한 작업도 요구사항 ID 없이 존재한다. 각각 `CONTRACT-*`, `AUDIT-*`처럼 출처를 명시해야 “근거 없는 범위 확장”과 구분할 수 있다.
3. **집계 루트 규칙이 일부 문서에서 일관되지 않다.** 평가 당시 스토리·옷장·Q&A 루트가 하위 업무를 가지면서 `isWork=true`였다. 루트 진행률과 실제 업무가 중복 집계될 여지를 없애야 한다.
4. **통합 관리 원장이 평가 대상 8개 문서 안에서 단일 기준으로 드러나지 않는다.** 문서별 분석이 좋아도 전체 누락·중복·교차 흐름은 별도 전역 원장과 최종 감사가 필요하다.

### 이 사례로 확정한 스킬 보강

- 반복 정책을 위한 Ref 카드 템플릿과 연결 게이트를 제공한다.
- 전역 소유권 원장을 단일 기준으로 삼고 각 요구사항 사본에 `주 소유/소비/참고` 역할을 표시한다.
- 구현 카드의 허용 출처를 요구사항, 공통 계약, 감사 발견, 문서 간 흐름 ID로 명시한다.
- 하위 업무가 있는 루트·묶음 카드는 집계 전용으로 두는 규칙을 회귀 점검 항목에 포함한다.

## 자동화 후보

다음 검사는 MindNProgress 문서 조회만으로 반복 가능하므로 자동화 우선순위가 높다. 2026-10-21 현재 일반 카드 편집 경로에서는 자동 실행되지 않으므로 최종 검증 때 수동으로 점검한다. 문서 재구성 제안 검증에서만 5와 7의 일부(집계 루트의 `isWork`, 대기 항목이 있는 카드의 완료)를 서버가 검사한다.

1. 전체 원본 단위 계수와 담당 문서 누락 검사
2. 요구사항별 주 소유 0개·2개 이상 검사
3. 구현 카드의 요구사항·계약·감사·흐름 ID 누락 검사
4. 적용 대상 UI 카드의 필수 정책 Ref 지식선 누락·방향·정책 검사
5. 하위 업무가 있는 루트·묶음 카드의 `isWork=true` 검사
6. 완료 요구사항의 구현 근거·필수 자동/Play 증거 누락 검사
7. 외부 차단 항목의 전달물·재개 조건 누락 검사
8. 총괄 원장·추적 카드에 반영되지 않은 위임 결과와 하위 결과가 있는데 0%로 남은 추적 카드 검사

자동 검사는 완료 판정을 대신하지 않는다. 이상 후보를 제시하고, 최종 판정은 원본과 최신 통합 결과를 확인한 독립 검수가 수행한다.
