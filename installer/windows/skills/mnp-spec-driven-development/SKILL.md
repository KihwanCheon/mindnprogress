# MindNProgress 기획서 기반 개발

기획서의 대표 기능만 구현한 프로토타입을 전체 완료로 오인하지 않도록, 원본 요구사항의 소유권과 구현·검증 증거를 끝까지 추적한다. 문서를 분할하더라도 요구사항이 빠지거나 중복되지 않고, 각 문서 담당자와 하위 실행자가 같은 기준으로 작업하는 것이 목표다.

## 용어

이 지침의 담당자·실행자·검수자는 현재 작업에 배정된 수행 역할을, 수행자는 그 역할을 실제로 수행하는 주체(카드에 연결된 AI 대화 등)를 뜻한다. 카드의 사람 담당자(`assigneeId`)와 Dooray 업무 담당자는 이 역할과 구분한다. 역할 이름은 아래 표를 단일 기준으로 쓰고, 다른 파일은 이 표를 참조한다.

| 역할 | 같은 역할의 다른 표기(도구 설명·전역 지침·이전 문서) | 담당 |
|---|---|---|
| 총괄 담당자 | 그룹 총괄, 공통 담당, 그룹 총괄 문서의 루트 AI | 최초 준비·계획과 최종 검증을 담당한다. 개발 중에는 승인된 문서별 계획을 문서 담당자에게 지시 전문으로 전달하고 공통 기준·계약·소유권 변경만 예외 조정한다. 다른 문서의 구현 카드에는 직접 위임하지 않는다. |
| 문서 담당자 | 문서 루트 담당자, 문서 담당, 대상 문서 AI, 루트 AI | 담당 원본 분석, 카드 구조 정비, 구현 위임과 문서 내부 검수를 담당한다. |
| 상위 담당자 | 상위 AI | 위임을 보낸 쪽(총괄·문서·묶음 카드 담당자)이다. 카드 계약·Ref 준비, 위임, 보고 수신·검수·인수를 담당한다. |
| 하위 실행자 | 하위 AI, 카드 AI, 구현 담당자, 하위 구현 담당 | 할당된 카드와 작업공간에서 구현·테스트·Play 증거를 만들고 결과를 보고한다. |
| 독립 검수자 | 검수자, 하위 검수 담당 | 원본과 요구사항 추적표에서 다시 시작해 구현 누락과 완료 판정을 확인한다. |
| 수신 담당자 | 후속 담당자, 다음 담당자 | 보고·인계를 받는 쪽이다. 위임 회신에서는 상위 담당자다. |

- **Play 검증**은 실제 실행 화면에서 표시·조작·전환을 확인하는 검증이다. Unity 프로젝트에서는 Unity Play를 뜻하고, 다른 프로젝트에서는 해당 앱의 실제 실행 화면 검증으로 읽는다. Prefab·씬·Unity 인스턴스 같은 표현도 Unity 프로젝트일 때의 기준이며, 다른 프로젝트에서는 화면·컴포넌트 소유 단위와 실행 환경으로 대응시킨다.
- 상태 값 문자열은 [요구사항 추적 규칙](references/requirement-traceability.md#상태-분류)의 표를 약칭 없이 그대로 쓴다.

## 역할별 진입

- 총괄 담당자, 공통 산출물을 받는 문서 담당자와 하위 실행자·독립 검수자는 [공통 문서 운영](references/common-document-workflow.md)을 먼저 읽는다. 실행 도구와 모델 종류에 관계없이 같은 규칙을 적용한다.
- 역할마다 먼저 읽을 최소 범위는 다음과 같다. 판단에 필요한 절이 더 있으면 그 절만 추가로 읽는다.

| 역할 | 최소 읽기 범위 |
|---|---|
| 총괄 담당자 | 이 문서 전체, 공통 문서 운영, 문서 분할과 통합 관리, 요구사항 추적 규칙, 위임과 검수 게이트 |
| 문서 담당자 | 이 문서 전체, 공통 문서 운영, 요구사항 추적 규칙, 최상위 카드 템플릿, 정책 Ref 카드 템플릿, 위임과 검수 게이트 |
| 하위 실행자 | 이 문서의 「용어」·「역할별 진입」·「권한과 확인」, 공통 문서 운영의 「역할별 적용」, 위임과 검수 게이트의 「상하위 카드 실행 경계」·「작업 결과 보고와 인수」·「구현 카드 최소 계약」·「카드 완료, 더미 완료와 제품 완료」·「완료 판정」의 「업무 카드 완료」(UI 카드는 「UI Play·시안 대조」 추가), 요구사항 추적 규칙의 「상태 분류」, 카드에 직접 연결된 Ref |
| 독립 검수자 | 하위 실행자 범위에 더해 위임과 검수 게이트의 「검수 층」·「완료 판정」 전체, 요구사항 추적 규칙 전체, 실패 유형과 방지 규칙 |
| 스킬·템플릿 개정자 | 이 스킬 전체와 회귀 평가 규칙과 기준 사례 |

- 공통 준비·계획, 기능 문서의 개발, 최종 검증 중 현재 역할에 해당하는 절차만 수행한다. 아래 전체 개발 흐름을 매 요청마다 처음부터 반복하지 않는다.
- 공통 결과를 받는 하위 업무는 담당 원본·Ref·구현 근거를 확인하며, 그룹 전체를 재분석하거나 미승인 문서 정비를 시작하지 않는다.
- 위임 작업의 결과를 회신하거나, 카드·문서·세션 사이에서 작업 결과를 인계·인수·재전달할 때는 [위임과 검수 게이트](references/delegation-and-validation.md#작업-결과-보고와-인수)의 「작업 결과 보고와 인수」를 따른다.

## 그룹 문서 지시

- 그룹 총괄 담당자가 승인된 문서별 계획을 소속 문서의 최상위 카드 담당자에게 전달할 때는 하위 업무 실행 위임과 구분하여 `mindnprogress_send_group_document_instruction`의 그룹 문서 지시를 사용한다.
- 총괄 담당자는 다른 문서의 구현 카드에 직접 위임하지 않는다. 문서 담당자가 전달받은 범위에서 카드 구조를 관리하고 자기 문서의 실제 하위 업무에 `mindnprogress_delegate_ai_work`를 사용한다.
- 지시에는 대상·그룹 및 문서 버전·작업 방향·승인 범위·실제 승인 근거·제외 범위·완료와 회신 조건을 포함하되, 도구가 따로 받는 값은 해당 필드에 한 번만 넣는다. 확인하지 못한 승인 근거를 만들지 않는다.
  - 사용자의 실제 승인 발언과 확인 가능한 출처: `approvalEvidence`. `instruction`에 반복하지 않는다.
  - 승인 범위: `approvalScope`(`analysis-only`, `card-maintenance`, `implementation`, `validation` 중 사용자에게 승인받은 최대 범위)
  - 그룹·문서 버전: `groupProjectVersion`, `targetRevision`
  - 회신 대상: `replyTarget`. 사용자가 이번 지시에 다른 대화를 명시한 경우에만 `explicit`을 쓴다.
  - 작업 방향·제외 범위·완료와 회신 조건, 이 스킬 이름과 먼저 읽을 Ref: `instruction`. 작성 요건은 [위임·지시 전문 작성](references/delegation-and-validation.md#위임지시-전문-작성)을 따른다.
- 문서 담당자의 최종 완료 보고는 `session-message`로 유효 회신 대상 대화(기본은 총괄 대화)에 한 번 직접 보낸다. 상세와 전송 실패 처리는 [위임과 검수 게이트](references/delegation-and-validation.md)의 「그룹 지시 회신」을 따른다.
- `queued`, `delivered`, `replied`는 지시 전달·응답 상태이고 `failed`, `cancelled`, `expired`는 전달 실패·취소·만료 상태다. 어느 값도 업무 완료 상태가 아니다. 실제 카드, 하위 위임, 구현·검증 증거를 기준으로 완료를 판정하고, 실패·취소·만료된 지시는 `reasonCode`와 `message`로 원인을 확인해 전달되지 않은 지시로 다룬다.
- 대상 문서 담당자가 범위 변경이나 새 실행을 제안하면 총괄 담당자가 스스로 승인하지 않고 사용자에게 재제안한다.

## 적용 모드

현재 요청에 맞는 모드를 선택한다.

- **신규 기획 개발**: 최신 원본에서 요구사항을 추출하고 문서 분할부터 시작한다.
- **기획 버전 갱신**: 현재 버전과 직전 버전, 기존 구현이 출발한 기준 버전을 비교해 영향받은 요구사항과 카드를 재개한다.
- **누락 복구 감사**: 이전 수행자의 완료 판정을 신뢰하지 않고 원본에서 다시 시작해 누락·부분 구현·오래된 동작을 재분류한다.

## 관련 스킬

- 원본이 PPTX이면 작업 전에 `pptx` 스킬을 읽는다. 최초 공통 준비는 전수 추출·확인하고, 소비 문서는 검증된 공용 산출물을 재사용하되 담당 범위의 이미지와 텍스트·표를 직접 대조한다. 전체 원본 분석·최종 검증에서는 모든 슬라이드를 확인한다.
- MindNProgress 카드·관계·댓글 또는 Dooray 업무를 다루기 전에 `mnp-dooray` 스킬을 읽는다.
- Unity UI를 제작하거나 Unity MCP를 사용할 때는 `unity-work` 스킬을 읽는다.

관련 스킬의 저장·권한·Unity 조작 규칙을 이 스킬에 중복해서 옮기지 않는다.

## 권한과 확인

- 분석·검토·순서 제안 요청은 MindNProgress 문서 생성·수정, 작업 위임이나 Dooray 기록 권한을 뜻하지 않는다.
- 사용자가 문서 구성 또는 구현 진행을 요청·승인한 범위에서만 해당 변경과 위임을 수행한다.
- 승인된 구현 범위가 기존 하위 업무 카드의 소유 범위라면 상위 담당자는 직접 구현하지 않고 해당 카드에 `mindnprogress_delegate_ai_work`로 위임한다. 이 위임은 필수 실행 경로이므로 직접 수행과 위임 중 무엇을 할지 다시 묻지 않는다. 상위 담당자가 대신하지 않는 일, 재승인 대상과 예외는 [상하위 카드 실행 경계](references/delegation-and-validation.md#상하위-카드-실행-경계)를 단일 기준으로 따른다.
- 문서 분할, 요구사항 소유권 또는 실행 순서의 선택이 결과를 크게 바꾸면 구현 착수 전에 선택안을 보여주고 확인받는다.

## 필수 게이트

다음 조건을 만족하기 전에는 구현 카드를 위임하지 않는다.

1. 최신 기획 원본과 버전이 식별됐다.
2. 담당 범위의 모든 원본 단위가 요구사항 목록 또는 `요구사항 없음/참고 시안`으로 기록됐다.
3. 요구사항마다 주 소유 문서가 정확히 하나다.
4. 기존 구현의 출발 버전부터 최신 버전까지의 차이와 직전 버전부터의 변경 영향이 분석됐다.
5. 현재 통합 기준의 기존 코드·Prefab·테스트가 요구사항별로 감사됐다.
6. 각 문서의 루트 실행 계약과 필요한 정책 Ref가 준비됐다.
7. 구현 카드가 담당 요구사항 ID와 독립적인 완료 조건을 가진다.

서버·최종 아트·사운드·정책이 대기 중이어도 요구사항을 삭제하지 않는다. 가능한 범위의 더미 클라이언트 완료와 외부 연동 완료를 분리한다.

## 실행 절차

### 1. 원본 기준 확정

- 사용자가 지정한 업무·첨부파일·경로에서 최신 원본과 수정 시각을 확인한다.
- 그룹 작업에서는 최신 그룹 문맥의 `project.sources` 전체를 확인하고, 각 원본의 주소·개별 버전과 관계를 구분한다. 첫 원본만 분석하거나 추가 원본을 대체본으로 간주하지 않는다.
- 최신 버전, 직전 버전, 기존 구현이 출발한 기준 버전을 원본별로 구분한다. 두 이전 버전이 같으면 중복 분석하지 않는다.
- 이미지에만 있는 상태, 화살표, 비활성 버튼, 오류 팝업, 주석과 예외도 요구사항 후보로 다룬다.
- 출처를 확인할 수 없거나 상충하면 임의로 최신 기준을 선택하지 않고 차이를 기록해 확인받는다.

### 2. 요구사항 전수 목록 작성

- 독립적으로 합격 여부를 판정할 수 있는 원자 단위로 분해한다.
- 버전 내부 출처 ID와 버전 간 추적용 요구사항 ID를 구분한다. 자세한 형식과 상태 분류는 [요구사항 추적 규칙](references/requirement-traceability.md)을 읽는다.
- 모든 슬라이드·페이지·절을 한 번 이상 계수한다. 내용이 없는 표지·챕터·시안 전용 페이지도 생략하지 않고 성격을 표시한다.

### 3. 문서 분할과 소유권 확정

- 슬라이드 수가 아니라 독립 완료 가능성, 공통 상태, 화면·Prefab 소유권, 서버 경계, 이벤트 생산·소비 관계와 병렬 작업 충돌을 기준으로 분할한다.
- 기존 공통·통합 문서를 최초 준비·계획과 최종 검증의 연결점으로 활용한다. 공용 코드·계약의 변경 소유 문서와 운영 역할은 구분하며, 이름이나 역할 변경만으로 문서를 새로 만들거나 삭제하지 않는다.
- 분할 기준과 통합 관리 문서 형식은 [문서 분할과 통합 관리](references/document-splitting.md)를 읽는다.
- 분할안, 소유권과 실행 순서가 사용자 결정에 영향을 주면 구현 전에 확인받는다.

### 4. MindNProgress 문서 부트스트랩

- 각 문서의 최상위 카드에 원본, 담당 범위, 분석 순서, 기존 구현 활용 규칙, 필수 Ref, 더미 구현 기준과 완료 게이트를 기록한다.
- [최상위 카드 템플릿](references/root-card-template.md)을 작업에 맞게 채운다. 필요 없는 절을 억지로 유지하지 않되 필수 게이트는 제거하지 않는다.
- 여러 문서와 하위 카드에 반복 적용할 제작·데이터·검수 규칙은 [정책 Ref 카드 템플릿](references/policy-ref-card-templates.md)에서 필요한 것만 골라 독립 지식 카드로 만든다.
- 문서 담당자가 먼저 분석 카드와 구현·후속 연동·검수 분기를 정비하게 한다.
- 하위 실제 업무를 가진 루트와 묶음 카드는 `isWork=false` 집계용으로 두고 직접 완료 처리하지 않는다. 진행률과 상태는 실제 하위 업무에서 파생되게 구성한다.
- 기존 카드가 있으면 삭제하거나 완료를 승계하지 않는다. 최신 요구사항과 명확히 대응되면 보완하고, 이력이 뒤섞여 추적이 어렵다면 최신 버전 재정비 분기를 만들고 기존 카드를 근거 Ref로 연결한다.

### 5. 분석 카드 완료

각 문서에는 필요에 맞게 다음 분석 결과가 있어야 한다. 출처·버전과 담당 범위가 확인된 공통 분석을 연결해 재사용할 수 있으나, 담당 요구사항 상세 검토와 현재 구현 감사는 각 문서가 수행한다. 결과가 이미 있다는 이유만으로 분석 카드를 복제하거나 완료를 승계하지 않는다.

- 최신 버전 담당 영역 원본 분석
- 기존 구현 출발 버전 → 최신 버전 전체 차이 분석
- 직전 버전 → 최신 버전 변경 영향 분석
- 현재 통합 구현·프로토타입 감사

기존 카드의 `done/100%`, 과거 커밋, 화면 캡처와 Play 결과는 재사용 후보일 뿐 최신 기획의 완료 증명이 아니다. 현재 코드 존재, 컴파일, 요구사항 정합과 재검증을 확인한 뒤에만 완료 근거로 사용한다.

### 6. 구현 카드 구성과 실행 순서

- 구현 카드는 요구사항 ID 전체, 변경 대상의 소유권, 재사용할 근거, 완료 조건과 검증 방법을 포함한다.
- 공통 계약을 최소 범위로 먼저 통합한 뒤 독립 화면·Provider를 병렬화하고, 기능 간 이벤트와 공유 Prefab 연결은 의존 순서로 통합한다.
- 같은 Prefab·공통 상태 파일을 여러 문서가 동시에 소유하지 않게 한다. 기능 문서는 독립 화면과 진입 계약을 제공하고, 공유 허브 연결은 지정된 소유 문서 또는 통합 카드에서 수행한다.
- UI 제작·변경·시각 검수 카드는 시안 정합 원칙 Ref를 대상 카드 방향으로 `reuse-first` 연결하고, 위임 전에 실제 연결을 재조회한다.
- 상세 위임·검수 규칙은 [위임과 검수 게이트](references/delegation-and-validation.md)를 읽는다.

### 7. 구현·검증

- 외부 데이터나 에셋이 없어도 결정적 Fixture/Provider와 더미 에셋으로 실제 진입, 상태 변화, 오류·재시도와 복귀가 가능한 Play 흐름을 만든다.
- 자동 검증은 정책·정렬·저장·대기열·재시작 경계를 담당한다.
- Play 검증(Unity 프로젝트에서는 Unity Play)은 표시·버튼·팝업·전환·재진입과 시안 정합을 담당한다.
- 하위 실행자의 diff 품질 검수와 별도로, 독립 검수자가 원본 요구사항 ID 전체를 기준으로 구현 여부를 다시 판단한다.

### 8. 완료와 버전 변경

- 업무 카드 완료, 더미 구현 완료, 외부 연동 완료와 문서·제품 완료를 구분한다. 더미 업무 카드만의 완료, 실제 연동·최종 리소스 카드의 분리 유지, 외부 대기 카드의 `done` 금지와 `waitingItems` 기록, 체크리스트 자동 상태, 루트·묶음 카드의 서버 자동 집계는 [카드 완료, 더미 완료와 제품 완료](references/delegation-and-validation.md#카드-완료-더미-완료와-제품-완료)를 단일 기준으로 따른다.
- 완료 판정은 [위임과 검수 게이트](references/delegation-and-validation.md#완료-판정)를, 종료 수치는 [요구사항 추적 규칙](references/requirement-traceability.md#종료-수치)을 따른다.
- 새 기획서가 등록되면 원본 단위와 요구사항별 변경을 비교하고 영향받은 카드·테스트를 재개한다. 슬라이드 번호가 같다는 이유로 같은 요구사항이라고 가정하지 않는다.

## 재발 방지 감사

이전 결과가 지나치게 작거나 구현 누락이 의심되면 [실패 유형과 방지 규칙](references/failure-prevention.md)을 읽고 원본부터 독립 감사한다. 동일 수행자의 자체 완료 보고나 넓은 체크리스트를 추가하는 것만으로 감사를 대체하지 않는다.

반대로 위임·검수가 반복되는데 담당 요구사항의 상태가 진척되지 않거나, 원본에 없는 범위가 구현으로 커지면 같은 문서의 [과잉 구현·요구사항 승격·준비 순환](references/failure-prevention.md#과잉-구현요구사항-승격준비-순환)의 중단 기준을 적용한다.

스킬·템플릿·작업 흐름 자체를 개선하거나 과거 실패 문서와 새 분할 문서를 비교할 때는 [회귀 평가 규칙과 기준 사례](references/regression-evaluation.md)를 읽는다. 특정 사례의 카드 수를 보편적 합격선으로 사용하지 않고, 커버리지·소유권·증거 불변조건을 검사한다.

## 작업 종료 보고

현재 작업 범위에 해당하는 다음 항목을 구분해 보고한다.
완료 판정에 필요한 항목을 확인하지 못했다면 미확인으로 명시한다.
위임 결과 회신과 작업 인계 보고에서는 「작업 결과 보고와 인수」에 따라 현재 판정과 근거를 연결한다.
아래 목록은 보고할 정보의 확인 항목이며, 각 항목의 상세 이력 전체를 매번 재전송하라는 뜻이 아니다. 구조화 보고에서는 괄호 안의 키에 적는다.

- 기준으로 사용한 기획 버전과 출처(`context`)
- 생성·정비한 문서와 담당 범위(`changes`)
- 요구사항 소유권과 구현 순서(`status`)
- 구현 위임 가능 여부(`status`)와 남은 게이트(`next.required`)
- 실제 연결한 정책·근거 Ref(`evidence`)
- [종료 수치](references/requirement-traceability.md#종료-수치)의 상태별 수치. 더미 구현 완료와 최종 구현 완료를 나눈다(`status`)
- 미분류·미검증 요구사항 수(`status`)
- 생성하거나 수정한 외부 업무(`changes`)와 사용자 확인이 필요한 결정(`next.required`)
